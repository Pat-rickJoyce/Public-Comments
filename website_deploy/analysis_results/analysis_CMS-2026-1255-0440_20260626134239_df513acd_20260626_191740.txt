## 1. COMMENTER INFORMATION

- **Author/Organization name:** HL7 Da Vinci Project Steering Committee, on behalf of HL7 Da Vinci Project membership
- **Stakeholder type:** Other - standards development/implementation accelerator with provider, payer, and technology vendor members
- **Credentials or expertise mentioned:** The commenter describes the Da Vinci Project as an HL7 Accelerator with more than 60 providers, payers, and technology vendors that develops FHIR implementation guides, sample code, and implementation support for value-based care and prior authorization workflows.

## 2. EXECUTIVE SUMMARY

HL7 Da Vinci strongly supports CMS and ONC movement toward required FHIR APIs, expansion of the Prior Authorization API to medical benefit drugs, continued use of NCPDP standards for pharmacy benefit drugs, and adoption of FHIR as the HIPAA prior authorization standard. Its central modifications are to avoid requiring specific IG versions before January 1, 2028, clarify version-expiration terminology, use SVAP and semantic versioning carefully, support endpoint and metric reporting with implementable technical approaches, and invest in testing, synthetic data, and right-sized certification.

## 3. REGULATORY CONTEXT

- **Specific provisions addressed:** PA-DRUG-MEDICAL; PA-DRUG-PHARMACY; FHIR-IG-REQUIRED; API-ENDPOINT-REPORTING; API-USAGE-METRICS; HIPAA-PA-STANDARDS; ONC-STANDARDS-UPDATE; GENERAL
- **Regulatory citations mentioned:** 45 CFR 170.215(j)-(n); 45 CFR 162.1301; 45 CFR 162.1201
- **Standards referenced:** HL7 FHIR; Da Vinci CRD, DTR, PAS, CDex, PDex, PDex US Drug Formulary, PDex Plan Net, ATR, HRex, and Unsolicited Notifications IGs; US Core; SMART App Launch; FAST Security; NCPDP SCRIPT; NCPDP RTPB; X12N 278; X12N 270/271; NDH IG; USCDI; SVAP; semantic versioning/SEMVER; CDS Hooks; SMART on FHIR.

## 4. DETAILED POSITIONS

**Topic 1: Medical Benefit Drug Prior Authorization via FHIR**
- **Provision ID:** PA-DRUG-MEDICAL
- **Position:** Support
- **Rationale:** Da Vinci supports adding drugs covered under the medical benefit to the FHIR-based Prior Authorization API because payers are already building infrastructure for CMS-0057-F and a common FHIR approach avoids duplicative burden.
- **Specific request:** Finalize inclusion of medical benefit drugs in the Prior Authorization API by the October 1, 2027 compliance date.

**Topic 2: Pharmacy Benefit Drug Prior Authorization via NCPDP**
- **Provision ID:** PA-DRUG-PHARMACY
- **Position:** Support
- **Rationale:** The commenter states that NCPDP RTPB and SCRIPT are already widely used and better suited for pharmacy benefit drugs arising from pharmacy prescriptions, while CRD/DTR/PAS are better suited for medical benefit items, services, and drugs.
- **Specific request:** Maintain the bifurcated standards approach: FHIR Da Vinci IGs for medical benefit drug prior authorization and NCPDP RTPB/SCRIPT for pharmacy benefit drug prior authorization.

**Topic 3: Mandatory FHIR IGs and Version Transition**
- **Provision ID:** FHIR-IG-REQUIRED; ONC-STANDARDS-UPDATE
- **Position:** Modify
- **Rationale:** Da Vinci supports requiring IGs to promote interoperable implementation, but warns that requiring specific IG versions before January 1, 2028 could disrupt CMS-0057-F implementation already underway using versions 2.0.1 or 2.1.0.
- **Specific request:** Allow any available versions of proposed IGs through at least January 1, 2028; make the newer listed versions the only required versions beginning January 1, 2028; clarify the regulatory meaning of expired because it differs from HL7 usage.

**Topic 4: SVAP, Semantic Versioning, and Standards Governance**
- **Provision ID:** ONC-STANDARDS-UPDATE; FHIR-IG-REQUIRED; HIPAA-PA-STANDARDS
- **Position:** Modify
- **Rationale:** Da Vinci supports SVAP but notes Da Vinci IGs do not mature on an annual cadence. It also explains that FHIR uses SEMVER and that patch updates should be usable without rulemaking or SVAP, while minor and major updates should proceed through SVAP and eventual rulemaking.
- **Specific request:** CMS and ONC should coordinate with Da Vinci and HL7 on SVAP timing, limit simultaneous versions, align with HL7 consensus processes, and explicitly adopt semantic-versioning expectations for HIPAA maintenance.

**Topic 5: Recommended IGs and Referenced IGs**
- **Provision ID:** FHIR-IG-REQUIRED; HIPAA-PA-STANDARDS
- **Position:** Support with clarification
- **Rationale:** Da Vinci supports recommending ATR for attribution, CDex for prior authorization attachments, and FAST Security for networked trusted exchange, while noting that FAST Security should supplement existing authentication options and that referenced IGs like HRex should inherit required or recommended status as applicable.
- **Specific request:** Recommend ATR, CDex, and FAST Security; clarify that IGs or standards referenced by a required or recommended IG are required or recommended accordingly; do not remove existing authentication and verification options before FAST harmonization is complete.

**Topic 6: Prior Authorization and API Metrics**
- **Provision ID:** API-USAGE-METRICS
- **Position:** Modify
- **Rationale:** Da Vinci supports reporting periods, annual aggregate de-identified reporting, numeric counts as well as percentages, and new drug PA metrics, but flags that pharmacy benefit denial-reason data may reside with PBMs or vendors rather than payers. It also wants metrics to capture when CRD or DTR prevents the need for a PAS submission.
- **Specific request:** Add numeric counts; clarify how to count CRD/DTR-based instant authorizations; capture submission method such as API, portal, fax, or phone; consider tracking Provider Access API opt-outs; publish reporting requirements as soon as possible.

**Topic 7: API Endpoint Reporting and Discovery**
- **Provision ID:** API-ENDPOINT-REPORTING
- **Position:** Modify
- **Rationale:** Da Vinci supports centralized endpoint publication but cautions that prior authorization can require multiple URLs for CRD, DTR, and PAS and multiple plan-specific URLs. It questions whether the NDH IG can represent the required multi-URL and metadata structure.
- **Specific request:** Continue requiring payer-discoverable endpoints outside CMS publication; evaluate a FHIR-based directory, HRex endpoint discovery, and other approaches before finalizing a specific IG for CMS endpoint reporting.

**Topic 8: HIPAA Prior Authorization Standards**
- **Provision ID:** HIPAA-PA-STANDARDS
- **Position:** Support with clarification
- **Rationale:** Da Vinci strongly supports replacing X12N 278 with FHIR standards and replacing X12N 270/271 only for the prior authorization need-determination use case. It stresses that CRD should not replace core eligibility, financial responsibility, network validation, claims preparation, or revenue cycle uses of X12N 270/271.
- **Specific request:** Finalize FHIR standards for HIPAA prior authorization, including US Core, SMART App Launch where applicable, CRD, DTR, PAS, and CDex; clearly preserve X12N 270/271 for non-prior-authorization eligibility uses and retain a hybrid model where X12N 271 supports HRex endpoint discovery.

**Topic 9: RFIs on Event Notifications, Testing, Certification, and Step Therapy**
- **Provision ID:** GENERAL
- **Position:** Modify
- **Rationale:** Da Vinci argues FHIR-based event notifications could improve on legacy ADT messages; comprehensive end-to-end testing, realistic synthetic data, and a national sandbox are needed; certification can help but should be right-sized; payer-to-payer APIs can help new payers honor prior step therapy progression.
- **Specific request:** Explore Da Vinci Unsolicited Notification IG for future event notifications; support longitudinal synthetic data and national sandbox testing; develop least-burdensome payer and EHR certification approaches; require use of previous payer information to advance step therapy continuity where appropriate.

## 5. SOLICITATION RESPONSES

- **S1:** Supports requiring IGs rather than leaving them recommended, because required IGs promote interoperable implementation of CMS APIs.
- **S2:** Supports use of updated IG versions but recommends flexibility through January 1, 2028 and specifically suggests PDex v2.2 may be the best version for the 2028 requirement.
- **S3:** Requests a clearer version transition policy, use of SVAP, coordination with HL7, and a clarified definition of expired/unexpired.
- **S12:** Supports adding medical benefit drugs to the FHIR Prior Authorization API and views the technical path as reasonable because the same infrastructure is being built for CMS-0057-F.
- **S14:** Supports maintaining NCPDP RTPB and SCRIPT for pharmacy benefit prior authorization because those standards are already widely used for pharmacy prescription workflows.
- **S15:** Strongly supports distinguishing medical benefit drugs from pharmacy benefit drugs and using separate standards optimized for each workflow.
- **S18:** Supports mandatory IGs but identifies implementation burden if specific versions are required too early or across inconsistent CMS/ONC programs.
- **S21:** States that the October 1, 2027 date for medical benefit drug prior authorization is reasonable.
- **S23:** Addresses security through support for FAST Security as a recommended IG for trusted networked exchange while cautioning that point-to-point and existing security mechanisms remain necessary.
- **S24:** Recommends endpoint reporting include enough detail for multiple API URLs, plan-specific URLs, documentation, and URL-level metadata.
- **S26:** Urges CMS to evaluate NDH, HRex endpoint discovery, and other FHIR-based options before prescribing the endpoint reporting format.
- **S27:** Notes that automated endpoint updating and discovery would be valuable, and CMS should ensure timing requirements are implementable.
- **S29:** Recommends numeric counts in addition to percentages, metrics by submission method, metrics for cases resolved through CRD/DTR without PAS, and a Provider Access API opt-out metric.
- **S30:** Supports annual aggregate, de-identified usage metric reporting.
- **S34:** Supports clarifying annual reporting schedules by impacted payer type.
- **S35:** Supports aggregate reporting because usage metrics help assess API value.
- **S44:** Strongly supports FHIR as the HIPAA prior authorization standard.
- **S45:** Supports extending FHIR prior authorization standards to all HIPAA covered entities to avoid divergent CMS and HIPAA standards.
- **S46:** Supports replacing X12N 278 with FHIR and partially replacing X12N 270/271 only for prior authorization need determination, while preserving other X12 eligibility uses.
- **S50:** Addresses IG maturity through version flexibility, SVAP, SEMVER, and clarification of referenced IGs such as HRex and CDex.
- **S53:** Implicitly supports phased transition by asking CMS not to lock in specific IG versions before January 1, 2028.
- **S54:** Calls for comprehensive end-to-end testing, realistic longitudinal synthetic data, a national sandbox, and right-sized certification.
- **S60:** Supports a semantic versioning approach in which patch updates can be used without rulemaking/SVAP and minor or major updates use SVAP and eventual rulemaking.
- **S61:** Urges CMS and ONC to coordinate with Da Vinci, HL7, and the broader community on version timing and standards updates.
- **S62:** Identifies current testing gaps and recommends deeper testing tools, synthetic data, and partner-based sandbox testing.
- **S63:** Requests clarification of the term expired and a transition process that does not prematurely eliminate usable IG versions.
- **S64:** Emphasizes HL7's open, consensus-based process and requests continued stakeholder engagement.
- **S65:** Notes implementers are already developing against CMS-0057-F IG versions and that some implementers are already using CDex in production.
- **S66-S82:** Responds to RFIs on event notifications, payer API implementation, payer IT certification, and step therapy by recommending FHIR-based notifications, national sandbox testing, right-sized certification, and use of payer-to-payer data to support continuity through step therapy.

## 6. RECOMMENDATIONS

1. Finalize medical benefit drug prior authorization through the FHIR Prior Authorization API by October 1, 2027.
2. Maintain NCPDP RTPB and SCRIPT for pharmacy benefit drug prior authorization.
3. Do not require specific IG versions before January 1, 2028; allow current implementation work to continue through 2027.
4. Clarify the regulatory use of expired/unexpired because it differs from HL7 terminology.
5. Coordinate SVAP and versioning with Da Vinci, HL7, ONC, and CMS program requirements.
6. Recommend ATR, CDex, and FAST Security, while preserving existing authentication options.
7. Clarify that IGs referenced by required or recommended IGs inherit the relevant required or recommended status.
8. Add numeric counts, submission-method measures, instant authorization handling, and opt-out measures to metric policy.
9. Publish API usage metric form-and-manner requirements quickly so payers and vendors can prepare.
10. Reassess endpoint reporting format and consider HRex endpoint discovery before finalizing an NDH-based approach.
11. Adopt FHIR for HIPAA prior authorization while preserving X12N 270/271 for non-prior-authorization eligibility functions.
12. Support comprehensive end-to-end testing, realistic synthetic data, national sandbox testing, and right-sized certification.
13. Explore FHIR-based event notifications and use payer-to-payer data to support step therapy continuity.

## 7. CONCERNS & OBJECTIONS

- **Primary concerns:** Premature IG version lock-in; inconsistent requirements across CMS-0057-F, this rule, and IPPS; ambiguity in expired terminology; endpoint reporting complexity; insufficient end-to-end testing infrastructure; pharmacy benefit metrics data being held by PBMs/vendors; overbroad replacement of X12N 270/271.
- **Potential negative impacts cited:** Interrupted implementation work, added provider/payer/vendor burden, confusion over compliant IG versions, incomplete metrics, endpoint discovery failures, duplicative standards, and unnecessary repetition of step therapy.
- **Implementation barriers mentioned:** Multiple API URLs, plan-level endpoints, NDH limitations, lack of realistic synthetic data, lack of comprehensive test suites, payer certification burden, external pharmacy partner data dependencies, and divergent program requirements.

## 8. SUPPORTING EVIDENCE

- **Data or statistics cited:** More than 60 Da Vinci Project member organizations; many payers, providers, and vendors have already begun CMS-0057-F development; several implementers are using CDex in production.
- **Studies or research referenced:** Not addressed.
- **Examples provided:** CRD/DTR resolving authorization needs without PAS; HRex endpoint discovery using X12N 270/271 PER segment and .well-known configuration; PDex v2.2 member match for attribution; FAST Security for trust networks; synthetic CRD test scenarios requiring aligned EHR and payer data; step therapy progression transferred through payer-to-payer exchange.

## 9. IMPACT ASSESSMENT

- **Affected stakeholders:** Impacted payers, all HIPAA covered entities, providers, EHR vendors, payer IT vendors, clearinghouses, PBMs, patients, and SDOs.
- **Economic implications:** The commenter expects automation and standards alignment to reduce burden, but warns premature version changes, certification, and pharmacy metrics collection could create unnecessary cost.
- **Technical feasibility:** Generally feasible if CMS preserves version flexibility, clarifies referenced standards, supports testing infrastructure, and chooses implementable endpoint reporting mechanisms.
- **Patient care impact:** The comment expects faster prior authorization, better care planning, fewer administrative delays, improved step therapy continuity, and more timely care.
