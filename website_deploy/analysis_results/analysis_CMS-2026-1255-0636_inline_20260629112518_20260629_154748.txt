## 2. EXECUTIVE SUMMARY
The commenter urges CMS to distinguish mere API conformance and usage from true interoperability completeness. They recommend oversight that evaluates whether payer-maintained USCDI data used for payment, risk adjustment, quality measurement, utilization management, or care management is also available through CMS-required interoperability APIs, while minimizing burden by leveraging existing audit and validation activities.

## 3. REGULATORY CONTEXT
- **Specific provisions addressed:** API-USAGE-METRICS, FHIR-IG-REQUIRED, GENERAL
- **Regulatory citations mentioned:** Not addressed
- **Standards referenced:** USCDI, CMS-required interoperability APIs, FHIR APIs

## 4. DETAILED POSITIONS
**Topic 1: Interoperability completeness versus API activity**
- **Provision ID:** API-USAGE-METRICS
- **Position:** Modify
- **Rationale:** API availability, transaction volume, and attestations do not prove that all payer-maintained clinical/USCDI data is accessible through APIs.
- **Specific request:** Future oversight should evaluate whether USCDI data exchanged between covered entities and maintained or used by payers is accessible through CMS-required APIs.

**Topic 2: Burden-minimizing oversight**
- **Provision ID:** GENERAL
- **Position:** Modify
- **Rationale:** New reporting programs could add administrative burden; existing audit and validation programs already review completeness, accuracy, and provenance of operational data.
- **Specific request:** Leverage quality measurement and risk adjustment validation activities to assess whether payer-held USCDI data is available through APIs.

## 5. SOLICITATION RESPONSES
- **S29-S30/S34-S35:** Responds indirectly to API usage metrics by arguing that activity and conformance metrics are insufficient unless paired with completeness/accountability measures.
- **S66-S82:** General oversight recommendation to evaluate interoperability completeness while minimizing burden through existing audit programs.

## 6. RECOMMENDATIONS
1. Distinguish API conformance/activity from interoperability completeness.
2. Assess whether payer-maintained USCDI data used for operational purposes is available through CMS-required APIs.
3. Avoid creating wholly new reporting programs where existing audit/validation activities can be leveraged.
4. Use quality measurement and risk adjustment validation frameworks to evaluate data completeness and provenance.

## 7. CONCERNS & OBJECTIONS
- **Primary concerns:** Payers may technically conform while excluding externally sourced or operationally used USCDI data from APIs.; API volume metrics may not measure whether APIs meet patient/provider data needs.
- **Potential negative impacts cited:** Incomplete patient/provider access to payer-maintained clinical data; misleading compliance metrics.
- **Implementation barriers mentioned:** Need to identify payer-maintained data, provenance, and whether it should be exposed through APIs without adding duplicative reporting burdens.

## 8. SUPPORTING EVIDENCE

## 9. IMPACT ASSESSMENT
- **Affected stakeholders:** Payers, Health IT developers, Patients, Providers, CMS oversight programs
- **Economic implications:** Could avoid duplicative administrative reporting if tied to existing audits; may require more robust payer data mapping and validation.
- **Technical feasibility:** Feasible if CMS defines completeness expectations and leverages existing validation processes.
- **Patient care impact:** Greater completeness could improve patient access, provider access, and reuse of data for treatment and related interoperability purposes.
