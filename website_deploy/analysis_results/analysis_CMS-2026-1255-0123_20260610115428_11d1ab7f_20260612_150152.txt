**2. EXECUTIVE SUMMARY**

EVRESA responds to RFI III.C by distinguishing API completeness from authority completeness. The comment supports standardized payer APIs but argues that APIs only prove a transaction occurred; they do not prove the authority, human review, evidence basis, patient identity governance, or reliability of the underlying PA decision, so CMS should recognize complementary governance-layer controls in future guidance.

**3. REGULATORY CONTEXT**

- **Regulatory citations mentioned:** CMS-0062-P; CMS-0057-F.
- **Standards referenced:** FHIR Da Vinci Prior Authorization Support (PAS); NCPDP SCRIPT; standardized payer APIs; FHIR/NCPDP composition; governance proof infrastructure; decision receipts; patient identity governance references.

**4. DETAILED POSITIONS**

**Topic 1: API-Authority Distinction**
- **Provision ID:** API-ENDPOINT-REPORTING; API-USAGE-METRICS; GENERAL
- **Position:** Clarify
- **Rationale:** Standardized APIs provide consistent data exchange, response formats, and transaction protocols, but they do not establish the authority basis for exchanged data.
- **Specific request:** CMS should recognize that PA APIs may need governance-layer controls above the API layer.

**Topic 2: API Completeness Versus Authority Completeness**
- **Provision ID:** PA-DENIAL-REASONS; FHIR-IG-REQUIRED; PA-DRUG-MEDICAL; PA-DRUG-PHARMACY
- **Position:** Modify/Clarify
- **Rationale:** A response can be technically API-complete while authority-incomplete; for example, a denial reason field may be populated without showing whether the denial reflected human judgment or automated inference.
- **Specific request:** Encourage authority completeness verification through governance attestations rather than changing API specifications.

**Topic 3: Patient Identity and Decision Provenance**
- **Provision ID:** GENERAL; HIPAA-PA-STANDARDS
- **Position:** Clarify
- **Rationale:** PA decisions reference patient identities across systems with different identity governance approaches; connecting identity, reviewer authority, evidence, and outcome is a governance issue not fully resolved by API standardization.
- **Specific request:** Consider governance-layer patient identity references that link PA events to decision receipts without replacing underlying identity systems.

**Topic 4: API Reliability Variation**
- **Provision ID:** API-ENDPOINT-REPORTING; API-USAGE-METRICS; GENERAL
- **Position:** Modify
- **Rationale:** CMS-0057-F implementation experience reportedly shows variation between robust APIs and technically compliant but fragile APIs, creating problems for entities dependent on consistent behavior.
- **Specific request:** Recognize network-level governance services that can detect incomplete or inconsistent API responses, route to human review, and produce attested resolution records.

**Topic 5: Network-Level Governance for Smaller Entities**
- **Provision ID:** GENERAL
- **Position:** Modify/Clarify
- **Rationale:** Entities with internal infrastructure can manage API reliability variation, while independent pharmacies and smaller providers may need network-level services to provide consistent attestation.
- **Specific request:** Recognize governance proof infrastructure as an architectural pattern, without mandating a specific API technology, vendor, or implementation architecture.

**5. SOLICITATION RESPONSES**

- **S23/S24/S26/S27/S33:** Indirectly relevant because payer API implementation, endpoint reliability, and technical reporting should be understood as transaction-layer capabilities that do not by themselves prove decision authority.
- **S29/S30/S34/S35:** Addresses API usage and reliability by emphasizing response completeness, consistency, and governance-layer reliability compensation.
- **S44/S45/S46:** Supports the FHIR/API-based approach while arguing that standardized transactions should coexist with governance controls for authority and evidence.
- **S50/S54/S55:** Recommends governance-layer controls related to authority attestation, identity references, and reliability compensation that could inform testing, certification, and enforcement discussions.
- **S51:** Identifies challenges for non-large entities, including independent pharmacies and smaller provider organizations that lack proprietary internal compliance infrastructure.
- **S66-S82:** This is a direct response to RFI III.C on improving payer API implementation technology.

**6. RECOMMENDATIONS**

1. Recognize in payer API or implementation guidance that standardized prior authorization APIs may benefit from governance-layer controls above the API layer.
2. Encourage documentation of authority attestation, evidence linkage, patient identity governance references, and authority completeness for PA decisions transmitted through APIs.
3. Distinguish API completeness from authority completeness in implementation guidance.
4. Allow governance attestations to address authority completeness without requiring changes to FHIR or NCPDP API specifications.
5. Consider governance-layer patient identity references that link identity, authority, evidence, and decision into auditable evidence packages.
6. Recognize network-level governance services as a way to compensate for inconsistent API reliability and support entities without internal compliance infrastructure.
7. Avoid mandating a specific API technology, vendor, or architecture.

**7. CONCERNS & OBJECTIONS**

- **Primary concerns:** APIs alone do not prove authority, human review, evidence basis, identity linkage, or decision provenance.
- **Potential negative impacts cited:** Technically compliant but authority-incomplete responses; denials that do not show human judgment; inconsistent or fragile API responses; downstream entities acting on incomplete or unreliable information.
- **Implementation barriers mentioned:** Variation in payer API reliability, incomplete or inconsistent responses, lack of internal compliance systems at independent pharmacies and smaller providers, and API fields not designed to carry authority-chain information.

**8. SUPPORTING EVIDENCE**

- **Data or statistics cited:** None.
- **Studies or research referenced:** Stakeholder reporting from CMS-0057-F implementation through 2025; EVRESA's foundational comment.
- **Examples provided:** FHIR PAS transaction transmitting a denial reason without proving authorized human medical judgment; NCPDP SCRIPT message transmitting PA status without documenting reviewer authority; API-complete denial reason field that remains authority-incomplete.

**9. IMPACT ASSESSMENT**

- **Affected stakeholders:** Impacted payers, providers, pharmacies, independent pharmacies, smaller provider organizations, infrastructure providers, patients, and technology vendors.
- **Economic implications:** Network-level governance services could reduce the cost of managing API variation for smaller entities and reduce burden from incomplete or unreliable responses.
- **Technical feasibility:** EVRESA proposes no changes to API specifications; governance proof would operate above FHIR/NCPDP APIs through attestations, decision receipts, identity references, and human-review routing.
- **Patient care impact:** More reliable authority and identity linkage could improve downstream confidence in PA decisions and reduce inappropriate action on incomplete or unreliable API data.
