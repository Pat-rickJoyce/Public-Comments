## 2. EXECUTIVE SUMMARY

This technically detailed comment from a payer-affiliated individual addresses multiple provisions across the rule, supporting the general direction but raising substantive concerns about FHIR standard maturity, HIPAA transaction changes, and regulatory clarity. The commenter strongly opposes replacing the X12 278 with CRD/DTR/PAS as a HIPAA standard and opposes proposed changes to the 270/271 transaction, arguing both transactions remain valuable and the 278 is used in over half of all PA requests per CAQH data. The commenter also raises concerns about FHIR IG maturity, FHIR version transition challenges, CARIN IG applicability, and the need for a standardized PA denial reason code list.

## 4. DETAILED POSITIONS

**Topic 1: Medical/Pharmacy Benefit Split Terminology**
- **Provision ID:** MEDICAL-VS-PHARMACY-BENEFIT
- **Position:** Clarify
- **Rationale:** "Medical benefit" and "pharmacy benefit" are vague terms. Tying the distinction to claim submission method is reasonable but creates edge cases where claims are submitted to the wrong entity and must be resubmitted.
- **Specific request:** Clarify the definition and acknowledge edge cases.

**Topic 2: FHIR Base Standard Must Be Named in Regulation**
- **Provision ID:** FHIR-IG-REQUIRED
- **Position:** Modify
- **Rationale:** Many FHIR R4 resources are not profiled under US Core or proposed IGs. Without naming the base FHIR standard in regulation, there is no definition for resources not covered by an IG.
- **Specific request:** Name the FHIR base standard (not just IGs) in regulation.

**Topic 3: FHIR Version Transition Challenges**
- **Provision ID:** FHIR-IG-REQUIRED, ONC-STANDARDS-UPDATE
- **Position:** Clarify
- **Rationale:** Many FHIR R4 resources are not normative and could change in R6 in breaking ways. Unlike X12 where messages are tied to specific versions, FHIR resources accumulated over time may need to be conveyed under a newer incompatible version.
- **Specific request:** Provide guidance on handling resources created under earlier FHIR versions when a new R version is named.

**Topic 4: CARIN IG Applicability to Provider Access and Payer-to-Payer APIs**
- **Provision ID:** FHIR-IG-REQUIRED
- **Position:** Oppose
- **Rationale:** CARIN IG for Blue Button 2.2.0 explicitly states it "does not directly address" Provider Access or Payer-to-Payer APIs. Requiring it for those APIs contradicts the IG's own scope.
- **Specific request:** Do not require CARIN IG for Provider Access and Payer-to-Payer APIs.

**Topic 5: FAST Security IG**
- **Provision ID:** FHIR-IG-REQUIRED
- **Position:** Oppose (as requirement)
- **Rationale:** Payers will follow internal risk/legal requirements; only appropriate after production use establishes liability certainty through case law.
- **Specific request:** Do not mandate FAST Security IG; limit recommendation to after production liability is established.

**Topic 6: RTPBC IG**
- **Provision ID:** PA-DRUG-PHARMACY
- **Position:** Modify
- **Rationale:** HHS should wait for current infrastructure to be used; payers will not implement unless required.
- **Specific request:** Wait to assess current infrastructure adoption; make required if CMS wants implementation.

**Topic 7: PA Decision Timeframe Auditability**
- **Provision ID:** PA-TIMEFRAMES-DRUGS
- **Position:** Clarify
- **Rationale:** "As the enrollee's health condition requires" is hard to measure or audit—unclear whether it is an API flag or inferred from clinical context.
- **Specific request:** Clarify operationalization and auditability of the expedited timeframe trigger.

**Topic 8: PA Denial Reason Code List**
- **Provision ID:** PA-DENIAL-REASONS
- **Position:** Modify
- **Rationale:** No standardized code list specified; without one, payers will use payer-specific lists, defeating standardization.
- **Specific request:** Name a specific standardized denial reason code list.

**Topic 9: API Endpoint Collection and Organization**
- **Provision ID:** API-ENDPOINT-REPORTING
- **Position:** Clarify/Oppose as proposed
- **Rationale:** Payers may prefer registration-gated endpoint disclosure. Without organizational guidance, the endpoint directory risks repeating the HPID/OEID enumeration problems.
- **Specific request:** Provide specific organizational guidance for the payer endpoint directory; consider registration-gated disclosure model.

**Topic 10: Provider Access API Statistics**
- **Provision ID:** API-USAGE-METRICS
- **Position:** Modify
- **Rationale:** Start simple until there is production experience, similar to how Patient Access API stats were phased in.
- **Specific request:** Start with minimal metrics and expand after production experience.

**Topic 11: Formulary Removal from Provider Access and Payer-to-Payer APIs**
- **Provision ID:** FHIR-IG-REQUIRED (cross-cutting)
- **Position:** Support
- **Rationale:** Formulary is not relevant for these APIs; removal is appropriate.

**Topic 12: HIPAA PA Standards — Replacing X12 278 with FHIR**
- **Provision ID:** HIPAA-PA-STANDARDS
- **Position:** Oppose
- **Rationale:** 278 used in over half of all PA requests per CAQH Indexes; forcing changes on trading partners for whom it works is unjustified. Current rules already allow FHIR for willing trading partners.
- **Specific request:** Do not replace 278 as HIPAA standard; if finalized, include enforcement discretion for continued 278 use by willing trading partners.

**Topic 13: 270/271 Transaction Changes**
- **Provision ID:** HIPAA-PA-STANDARDS
- **Position:** Oppose
- **Rationale:** The 270/271 is heavily used and effectively conveys PA information. X12 8060 adds even more PA capability. Proposed redefinition creates confusion and could force providers to run both 270/271 and CRD where one transaction currently suffices.
- **Specific request:** Leave 270/271 definition unchanged; if CRD is named a HIPAA standard, give it a distinct transaction name without altering the 270/271; align changes with X12 8060 compliance date.

**Topic 14: Referrals in CRD/DTR/PAS**
- **Provision ID:** FHIR-IG-REQUIRED
- **Position:** Oppose
- **Rationale:** Not proven in production; well-established 278 transaction handles referrals.
- **Specific request:** Do not include referrals in CRD/DTR/PAS named functions.

**Topic 15: Major.Minor.Patch Versioning**
- **Provision ID:** ONC-STANDARDS-UPDATE
- **Position:** Oppose
- **Rationale:** Allowing changes without rulemaking would undermine the same process applied to other SDOs.
- **Specific request:** Require rulemaking for all FHIR IG version changes.

**Topic 16: FHIR IG Maturity Generally**
- **Provision ID:** FHIR-IG-REQUIRED
- **Position:** Oppose (mandatory adoption)
- **Rationale:** None of the IGs have had sufficient large-scale production experience; X12 had 10+ years in production before HIPAA adoption.
- **Specific request:** Do not mandate IGs lacking sufficient production track record.

**Topic 17: Direct Data Entry Exception**
- **Provision ID:** PA-DRUG-MEDICAL, PA-DRUG-PHARMACY
- **Position:** Support
- **Rationale:** Serves as "break glass" mechanism when other systems fail.
- **Specific request:** Maintain the exception as-is.
