# Comment Analysis Template: CMS-2026-1255-0001

## 1. COMMENTER INFORMATION

- **Author/Organization name:** Sheer Health.
- **Stakeholder type:** Technology Vendor.
- **Credentials or expertise mentioned:** Sheer Health describes itself as a New York City healthcare technology company that helps patients understand and use health insurance benefits, resolve billing errors, manage claims, maximize benefits, and use plan coverage, claims history, and PA data.

## 2. EXECUTIVE SUMMARY

Sheer Health strongly supports the proposed interoperability changes, especially patient access API improvements and access to prescription drug prior authorization data. It recommends adding RTPBC IG support for Patient Access APIs, expanding the payer scope to state-based exchange issuers where possible, and strengthening payer API testing, access, downtime/error reporting, and certification.

## 3. REGULATORY CONTEXT

- **Specific provisions addressed:** FHIR-IG-REQUIRED; PA-DRUG-PHARMACY; API-USAGE-METRICS; FF-SHOP-REQUIREMENTS; GENERAL/RFI on improving payer API implementation.
- **Regulatory citations mentioned:** 91 FR 19890; Section II.A Interoperability Standards for APIs; Section II.D.3 FF-SHOP Patient Access APIs; Section I.C Specific Terms; RFI III.C Improving Implementation of Payer API Technology.
- **Standards referenced:** Patient Access API; CARIN IG for Blue Button; PDex IG; PDex US Drug Formulary IG; RTPBC IG; payer API certification; sandbox and production API environments.

## 4. DETAILED POSITIONS

**Topic 1: Patient Access API Interoperability Standards**
- **Provision ID:** FHIR-IG-REQUIRED; PA-DRUG-PHARMACY
- **Position:** Support
- **Rationale:** Prescription drug PA data will improve transparency and help patients and advocates understand coverage.
- **Specific request:** Finalize patient access API standards and access to prescription drug PA data.

**Topic 2: Required Use of Unexpired IG Versions**
- **Provision ID:** FHIR-IG-REQUIRED
- **Position:** Support
- **Rationale:** Inconsistent patient access APIs make it harder for patients and third parties to create unified cross-payer experiences.
- **Specific request:** Require conformance to unexpired versions of CARIN IG for Blue Button, PDex IG, and PDex US Drug Formulary IG, with automatic incorporation of updated versions.

**Topic 3: RTPBC IG for Patient Access APIs**
- **Provision ID:** FHIR-IG-REQUIRED; GENERAL
- **Position:** Modify
- **Rationale:** Third-party apps need medication cost and coverage data to help patients afford and understand medications.
- **Specific request:** CMS should recommend RTPBC IG for the Patient Access API.

**Topic 4: Expand Impacted Payer Scope**
- **Provision ID:** FF-SHOP-REQUIREMENTS
- **Position:** Modify
- **Rationale:** Many plans do not expose APIs, excluding patients from interoperability benefits and increasing developer burden.
- **Specific request:** Expand requirements beyond FF-SHOP small group QHP issuers by reconsidering exclusion of SBE issuers, assessing overlap with FFE issuers, and incentivizing SBEs where CMS cannot mandate APIs.

**Topic 5: API Testing and Environment Consistency**
- **Provision ID:** GENERAL; API-USAGE-METRICS
- **Position:** Modify
- **Rationale:** Differences between sandbox and production behavior, and inconsistencies among a payer's plans, make implementation difficult.
- **Specific request:** Require payer API testing for consistency across multiple plans and across sandbox and production environments.

**Topic 6: Developer Access, Reliability Metrics, and Certification**
- **Provision ID:** API-USAGE-METRICS; GENERAL
- **Position:** Modify
- **Rationale:** Production API access can take weeks, developer portals and APIs can fail or go down, and third parties need a clear way to identify compliant APIs.
- **Specific request:** Standardize API access processes and timelines, require downtime and error-rate reporting, test frequently across functions, and require certification if ONC establishes payer API criteria, with optional higher levels of certification.

## 5. SOLICITATION RESPONSES

- **S1/S2/S3/S6/S37:** Sheer Health supports requiring unexpired versions of CARIN Blue Button, PDex, and PDex US Drug Formulary IGs and supports version updating to reduce inconsistent API behavior.
- **S8/S25:** The recommendation to support RTPBC IG for Patient Access APIs relates to real-time prescription benefit and medication cost/coverage transparency.
- **S40/S41/S42:** Sheer supports expanding API requirements to FF-SHOP small group QHP issuers and asks CMS to go further by considering SBE issuers and incentives for non-mandated payers.
- **S29/S30/S34/S35:** Sheer recommends collecting API downtime and error rates in addition to usage metrics, with frequent testing that detects sporadic breakages.
- **S62/S65:** Sheer supports payer API certification and testing criteria, recommending required certification if ONC establishes criteria and optional higher certification levels to encourage robust APIs.
- **S66-S82:** Sheer responds to RFI III.C on improving payer API implementation through sandbox/production consistency testing, standardized developer onboarding, reliability reporting, and certification.

## 6. RECOMMENDATIONS

1. Finalize patient access API interoperability standards and access to prescription drug PA data.
2. Require conformance to unexpired versions of CARIN IG for Blue Button, PDex IG, and PDex US Drug Formulary IG.
3. Preserve automatic incorporation of updated versions into standards.
4. Recommend RTPBC IG for the Patient Access API.
5. Expand required Patient Access APIs to additional payers wherever CMS has authority.
6. Reconsider continued exclusion of SBE issuers and evaluate whether FFE participation can support broader issuer portfolio requirements.
7. Incentivize SBEs to implement APIs where mandates are unavailable.
8. Require API testing for consistency across plans and between sandbox and production environments.
9. Standardize and streamline third-party production API access processes and timelines.
10. Require payers to report API downtime and error rates.
11. Use testing mechanisms with broad functional coverage and frequent runs.
12. Require payer API certification if ONC establishes criteria, while allowing voluntary higher certification tiers.

## 7. CONCERNS & OBJECTIONS

- **Primary concerns:** Inconsistent API behavior, limited payer scope, lack of medication cost/coverage data, slow and variable developer access processes, API downtime/errors, and lack of clear certification signals.
- **Potential negative impacts cited:** Patients may be unable to use third-party applications, third-party developers face higher workload, and patients lack clear access to coverage and medication affordability information.
- **Implementation barriers mentioned:** Differences among payer APIs, sandbox/production mismatch, multi-week production access processes, unreliable developer portals, and absence of consistent certification.

I. Introduction

Sheer Health is a healthcare technology company based in New York City dedicated to helping patients understand how to use their health insurance benefits with ease. Our technology allows us to advocate for members in resolving billing errors, managing claims, and maximizing their benefits. Sheer Health's primary mission revolves around ensuring that accessing healthcare is simple, transparent, and easy to understand. Data such as plan coverage information, claims history, and prior authorizations are critical to our operations.

Sheer Health voices strong support of this proposed rule and the changes it would make to interoperability standards, with some additional recommendations and observations.
