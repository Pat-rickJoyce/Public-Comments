# Comment Analysis Template: CMS-2026-1255-0001

## 1. COMMENTER INFORMATION

- **Author/Organization name:** Fallon Health (H9001).
- **Stakeholder type:** Payer.
- **Credentials or expertise mentioned:** No individual signer or credentials provided in the extracted text. Fallon comments from the perspective of an impacted payer operating API and authorization workflows.

## 2. EXECUTIVE SUMMARY

Fallon Health supports CMS's interoperability goals and a centralized API inventory, but recommends restricting access to detailed endpoint and technical information for security reasons. It also urges CMS to address FHIR PAS gaps for iterative prior authorization updates before replacing X12 278, and recommends risk-based, standards-aligned approaches for resiliency, security, testing, oversight, and enforcement.

## 3. REGULATORY CONTEXT

- **Specific provisions addressed:** API-ENDPOINT-REPORTING; HIPAA-PA-STANDARDS; ONC-STANDARDS-UPDATE; GENERAL/RFIs.
- **Regulatory citations mentioned:** No CFR citations. The comment references Section II.H, Section II.I, and RFI sections III.B and III.C.
- **Standards referenced:** FHIR, FHIR capability statements, FHIR PAS, X12 278, NIST, HIPAA security requirements, OAuth 2.0, ONC certification.

## 4. DETAILED POSITIONS

**Topic 1: Centralized API endpoint inventory access controls**
- **Provision ID:** API-ENDPOINT-REPORTING
- **Position:** Modify
- **Rationale:** Fallon supports centralized API discovery but warns that unrestricted publication of endpoint URLs and technical details may reduce the effort required for large-scale or automated targeting.
- **Specific request:** Maintain a centralized API inventory with restricted access for regulated entities, registered developers, providers, and CMS-authorized users; if public publication is required, disclose only the minimum necessary technical detail.

**Topic 2: HIPAA PA standards and FHIR PAS workflow completeness**
- **Provision ID:** HIPAA-PA-STANDARDS
- **Position:** Modify / Clarify
- **Rationale:** Fallon views transition from X12 278/manual workflows to FHIR APIs as positive, but says real-world authorization workflows often require iterative updates and additional documentation after initial submission.
- **Specific request:** Standardize FHIR PAS support for ongoing updates and post-submission attachments before removing or replacing X12 278.

**Topic 3: Health care resiliency RFI**
- **Provision ID:** GENERAL
- **Position:** Clarify / Modify
- **Rationale:** Fallon recommends using existing security, continuity, and breach-response frameworks rather than creating duplicative requirements.
- **Specific request:** Align FHIR API security with NIST/HIPAA, use controls such as encryption and OAuth 2.0, require risk-based testing, maintain business continuity plans scaled to organizational risk, and follow established breach notification and post-incident review practices.

**Topic 4: Payer API implementation RFI**
- **Provision ID:** GENERAL; ONC-STANDARDS-UPDATE
- **Position:** Modify
- **Rationale:** Fallon favors validation and oversight that are risk-based, industry-led, and aligned with existing ONC certification, rather than broad new CMS-specific mandates.
- **Specific request:** Align testing with ONC certification, limit CMS-specific testing to high-risk scenarios, standardize flexible API performance reporting, promote periodic trading-partner testing, provide an optional CMS registry, and focus enforcement on collaborative remediation.

## 6. RECOMMENDATIONS

1. Proceed with a centralized API inventory but restrict access to users with a legitimate need.
2. Limit public disclosure, if any, to the minimum technical information necessary for interoperability.
3. Avoid requiring implementation-specific or operationally sensitive API information where practicable.
4. Standardize FHIR PAS support for iterative updates and post-submission attachments before replacing X12 278.
5. Align FHIR API security expectations with NIST and HIPAA requirements.
6. Use encryption, OAuth 2.0, and periodic risk-based security testing.
7. Maintain business continuity plans with redundancy and recovery objectives scaled to organization size and risk.
8. Follow breach notification rules and encourage post-incident reviews.
9. Align API testing with ONC certification and industry-led validation.
10. Use flexible, phased API performance reporting and periodic risk-based trading-partner testing.
11. Provide optional CMS registry visibility using automated reporting where feasible.
12. Use collaborative remediation first and reserve penalties for persistent or high-impact noncompliance.

Comments on CMS-0062-P from Fallon Health (H9001)

II. Provisions of the Proposed Rule
H. Reporting Payer API Endpoints and Associated Information for CMS To Publish

CMS 0062 P proposes to require impacted payers to report API endpoints, FHIR capability statement URLs, and associated technical documentation for publication by CMS in a centralized location. We support CMS's goal of improving interoperability and agree that a centralized inventory of payer APIs is reasonable and may facilitate discovery and adoption.

Our comments focus on how this inventory is made available from an information security perspective.

We recommend that CMS maintain the centralized API inventory with restricted access limited to parties with a legitimate need, such as regulated entities, registered application developers, providers, and other CMS authorized users, rather than publishing detailed endpoint and technical information for unrestricted public access.
