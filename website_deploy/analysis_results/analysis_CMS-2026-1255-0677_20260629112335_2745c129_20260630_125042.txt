## 1. COMMENTER INFORMATION

- **Author/Organization name:** Not provided; commenter proposes a Network Identification Number (NIN) framework.
- **Stakeholder type:** Individual / Other (standards proposal; likely health IT/interoperability stakeholder)
- **Credentials or expertise mentioned:** No formal credentials stated. The comment demonstrates familiarity with FHIR, Transparency in Coverage files, SMART Health Links, CARIN Blue Button, provider directories, claims, and payer network operations.

## 2. EXECUTIVE SUMMARY

The commenter proposes creation of a structured Network Identification Number (NIN) to give health plan networks a stable, computable identity across Transparency in Coverage files, provider directories, digital insurance cards, coverage records, and claims. The comment is broadly supportive of FHIR-based interoperability infrastructure but asks CMS to address a gap not directly covered by the proposed drug prior authorization rule: consistent identification of payer networks for transparency, in-network status, cost estimation, and directory accuracy.

## 3. REGULATORY CONTEXT

- **Specific provisions addressed:** FHIR-IG-REQUIRED; API-ENDPOINT-REPORTING; ONC-STANDARDS-UPDATE; GENERAL.
- **Regulatory citations mentioned:** No CFR citations mentioned. The comment refers generally to Transparency in Coverage requirements and the No Surprises Act.
- **Standards referenced:** FHIR; FHIR InsurancePlan, Coverage, ExplanationOfBenefit, PractitionerRole, OrganizationAffiliation, Location, and Subscription resources; SMART Health Links; CARIN Blue Button; Legal Entity Identifier (LEI) and GLEIF Global LEI Index.

## 4. DETAILED POSITIONS

**Topic 1: Standard Network Identification Number**
- **Provision ID:** GENERAL
- **Position:** Modify
- **Rationale:** The commenter argues that plan network names are marketing labels that do not map consistently across directories, rate files, eligibility systems, claims, and digital insurance cards. This inconsistency undermines consumer cost estimation, directory accuracy, surprise billing protections, and regulatory oversight.
- **Specific request:** CMS should adopt or facilitate development of a structured NIN schema that uniquely identifies network instances using standardized, public elements.

**Topic 2: FHIR Implementation of Network Identity**
- **Provision ID:** FHIR-IG-REQUIRED
- **Position:** Clarify / Modify
- **Rationale:** The commenter states that existing FHIR infrastructure is mature enough to carry NINs and that the InsurancePlan resource can serve as the authoritative record, with NINs propagated through Coverage, ExplanationOfBenefit, PractitionerRole, and OrganizationAffiliation resources.
- **Specific request:** CMS should recognize a standard FHIR implementation pattern for NINs, using native FHIR fields where available and standard extensions where necessary.

**Topic 3: Transparency in Coverage and Directory Accuracy**
- **Provision ID:** API-ENDPOINT-REPORTING
- **Position:** Modify
- **Rationale:** The commenter argues that current TiC files cannot reliably support consumer tools because rates are associated with inconsistent plan or network labels. A NIN would allow public endpoints, directories, and rate files to reference the same network.
- **Specific request:** CMS should use a standard network identifier as an anchor when restructuring TiC machine-readable files and related public API artifacts.

**Topic 4: Provider Participation Query and Notification**
- **Provision ID:** ONC-STANDARDS-UPDATE
- **Position:** Clarify
- **Rationale:** The commenter describes how NIN-keyed FHIR directory records could support yes/no queries about provider participation and enable FHIR Subscription-based notifications when network participation changes.
- **Specific request:** CMS and ONC should support standard resource usage and vocabulary needed for NIN-keyed provider directory lookup and network participation change notifications.

- **S66-S82:** The comment is best treated as a general interoperability RFI response proposing a new network identity layer for transparency, directories, digital cards, claims, and notifications.

## 6. RECOMMENDATIONS

1. Establish a Network Identification Number as a stable, structured identifier for health plan network instances.
2. Build the NIN schema from public, consumer- and regulator-relevant elements rather than internal contracting or risk-sharing details.
3. Represent the NIN in FHIR InsurancePlan as the authoritative network record and propagate it through Coverage, ExplanationOfBenefit, PractitionerRole, and OrganizationAffiliation resources.
4. Require or encourage payers to map internal provider panel records to NINs and publish NIN-keyed provider participation records with effective and end dates.
5. Use NINs to anchor restructured Transparency in Coverage files, provider directory accuracy monitoring, digital insurance cards, and network adequacy oversight.
6. Support NIN-based yes/no provider participation queries and FHIR Subscription notifications for network changes.

## 7. CONCERNS & OBJECTIONS

- **Primary concerns:** Existing network names are inconsistent across payer systems and public artifacts; TiC files are hard to use; multi-network plan designs are not computable; provider participation status cannot be queried reliably.
- **Potential negative impacts cited:** Consumers may rely on directories that do not match claims adjudication and receive surprise bills; developers must create payer-specific logic; providers discover network changes through delayed claims or portal lookups; regulators cannot easily connect rate files, directories, complaints, and adequacy filings.
- **Implementation barriers mentioned:** Payers must map internal panel records to NINs, publish accurate NIN-keyed FHIR directories, retain version history, and maintain timely participation data.
