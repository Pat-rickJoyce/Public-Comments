# Comment Analysis Template: CMS-2026-1255-0001

## 1. COMMENTER INFORMATION

- **Author/Organization name:** HealthLX; submitted by Will Tesch, CEO
- **Stakeholder type:** Technology Vendor
- **Credentials or expertise mentioned:** Health IT vendor providing FHIR-based interoperability and prior authorization services to health plans; founding member of the HL7 Da Vinci Project; contributor to reference implementations; experience supporting CMS-9115-F, CMS-0057-F, and CMS-4208-F compliance.

## 2. EXECUTIVE SUMMARY

HealthLX strongly supports the proposed rule's direction, including drug prior authorization expansion, HIPAA adoption of FHIR for prior authorization, centralized endpoint reporting, and ONC-aligned standards versioning. It recommends targeted modifications to make implementation practical: require use-case-specific IGs rather than overlapping base standards, phase immature components, build a FHIR/NDH endpoint registry, preserve version transition windows, and require objective conformance testing.

## 3. REGULATORY CONTEXT

- **Specific provisions addressed:** FHIR-IG-REQUIRED; PA-DRUG-MEDICAL; PA-DRUG-PHARMACY; API-ENDPOINT-REPORTING; API-USAGE-METRICS; FF-SHOP-REQUIREMENTS; HIPAA-PA-STANDARDS; ONC-STANDARDS-UPDATE; GENERAL.
- **Regulatory citations mentioned:** 45 CFR 170.215; 45 CFR 162.923(b); HIPAA Administrative Simplification; references to CMS-9115-F, CMS-0057-F, CMS-4208-F, and CMS-0062-P.
- **Standards referenced:** FHIR, Da Vinci CRD, DTR, PAS, CDex, FAST Security IG, SMART App Launch, Tiered OAuth, UDAP, CARIN RTPBC, PDex US Drug Formulary, NCPDP SCRIPT, Formulary & Benefit, RTPB, NDH Endpoint Profile, X12N 278, X12N 270/271, HL7 Major.Minor.Patch, Inferno, TEFCA/QHIN, NIST.

## 4. DETAILED POSITIONS

**Topic 1: Required FHIR IGs and capability scoping**
- **Provision ID:** FHIR-IG-REQUIRED
- **Position:** Modify
- **Rationale:** Use-case IGs already constrain base FHIR versions; naming both base FHIR and IGs creates version drift and ambiguity. Open-ended IG conformance also forces unused development.
- **Specific request:** Require use-case-specific IGs and treat base FHIR as incorporated through them; publish scoped capability sets in sub-regulatory guidance.

**Topic 2: FAST Security and CDex maturity**
- **Provision ID:** FHIR-IG-REQUIRED; HIPAA-PA-STANDARDS
- **Position:** Modify
- **Rationale:** FAST Security and CDex are directionally correct but not yet mature enough for immediate mandatory adoption at scale.
- **Specific request:** Keep FAST Security and CDex recommended for now, signal intent to require later, and use production deployment, trust-community, and connectathon/test results as readiness criteria.

**Topic 3: Pharmacy benefit standards**
- **Provision ID:** PA-DRUG-PHARMACY
- **Position:** Support
- **Rationale:** NCPDP SCRIPT, F&B, and RTPB align non-Part D programs with established Part D practice and serve distinct, non-duplicative functions.
- **Specific request:** Retain both F&B and RTPB; set expectations for timely F&B updates, such as weekly and promptly after prior authorization indicator changes.

**Topic 4: Medical benefit drugs and routing**
- **Provision ID:** PA-DRUG-MEDICAL; MEDICAL-VS-PHARMACY-BENEFIT
- **Position:** Support with clarification
- **Rationale:** Reusing CRD/DTR/PAS for medical benefit drugs avoids parallel infrastructure, but edge cases arise when a drug may be covered under either benefit.
- **Specific request:** Use claims-adjudication pathway as the default rubric, pair it with a machine-readable CRD CoverageInformation routing signal, and confirm that dual-pathway drugs can appear in both workflows without noncompliance.

**Topic 5: API endpoint reporting**
- **Provision ID:** API-ENDPOINT-REPORTING
- **Position:** Support with modifications
- **Rationale:** Endpoint discovery is a major practical barrier; a centralized directory would reduce integration friction.
- **Specific request:** Use a FHIR-enabled registry aligned with the NDH Endpoint Profile; avoid redundant capability statement URL reporting; collect structured auth details; extend initial reporting to 90 days and allow 30 days for manual updates until automated reporting is available.

**Topic 6: API usage and public metrics**
- **Provision ID:** API-USAGE-METRICS
- **Position:** Support
- **Rationale:** Usage metrics are essential for measuring adoption, especially the percentage of prior authorization requests received through the Prior Authorization API.
- **Specific request:** Retain PA API adoption metrics, support FHIR-based automated reporting, allow transitional portal/form reporting for small plans, and treat metrics as complementary to conformance testing.

**Topic 7: Standards versioning and expiration**
- **Provision ID:** ONC-STANDARDS-UPDATE; FHIR-IG-REQUIRED
- **Position:** Support with clarification
- **Rationale:** Cross-referencing ONC-approved versions reduces lag between standards maturity and permitted use. Hard cutovers without overlap would break production integrations.
- **Specific request:** Permit compatible Minor.Patch IG versions without new rulemaking and retain at least 12-18 months of transition overlap before older versions expire.

**Topic 8: HIPAA adoption of FHIR for prior authorization**
- **Provision ID:** HIPAA-PA-STANDARDS
- **Position:** Support with limits
- **Rationale:** FHIR-based HIPAA standards align HIPAA transactions with CMS API mandates, but broad replacement of X12 eligibility is premature.
- **Specific request:** Adopt FHIR for prior-authorization-related X12N 278 and narrow 270/271 prior authorization checks, retain X12 270/271 for other eligibility uses, preserve coexistence, and phase down the direct data entry exception only after maturity is demonstrated.

**Topic 9: Small plans, vendors, PBMs, and delegated entities**
- **Provision ID:** GENERAL; SMALL-PAYER-IMPACT
- **Position:** Clarify
- **Rationale:** Payers depend on PBMs, delegated entities, and vendors for data and operations; small plans have limited technical capacity.
- **Specific request:** Confirm compliance can be achieved through vendors/delegates, require data holders such as PBMs to support standards, allow accommodations for delegated-entity readiness gaps, support aggregated vendor submissions, and fund reference implementations and low-cost test tooling.

**Topic 10: Payer API implementation RFI and conformance**
- **Provision ID:** GENERAL; API-USAGE-METRICS; API-ENDPOINT-REPORTING
- **Position:** Modify
- **Rationale:** The main barrier is inconsistent conformance, including semantic variance, not lack of standards.
- **Specific request:** Require standardized automated conformance testing, leverage ONC Certification, monitor production availability/conformance, use PA API adoption metrics as oversight signals, and test registration/authorization flows against real-world clients.

**Topic 11: Cybersecurity and resiliency RFI**
- **Provision ID:** GENERAL
- **Position:** Support with clarification
- **Rationale:** Expanded API data exchange increases security and resiliency stakes.
- **Specific request:** Standardize authentication through FAST/UDAP over time, reduce one-off point-to-point connections, require graceful degradation and incident expectations, and align new requirements with HIPAA Security Rule and NIST rather than creating duplicative regimes.

## 6. RECOMMENDATIONS

1. Require use-case-specific IGs and treat base FHIR versions as incorporated through those IGs.
2. Scope required IG capabilities by use case and publish capability sets in refreshable guidance.
3. Keep FAST Security and CDex recommended until production maturity, trust infrastructure, and testing support mandatory use.
4. Retain NCPDP SCRIPT, F&B, and RTPB for pharmacy benefit drugs and define F&B update latency expectations.
5. Use CRD CoverageInformation to route drugs between FHIR medical benefit and NCPDP pharmacy benefit workflows.
6. Build endpoint reporting as a FHIR-enabled registry aligned with the NDH Endpoint Profile.
7. Remove redundant capability-statement URL reporting and collect structured authentication details.
8. Extend initial endpoint reporting to 90 days and provide a longer manual-update window while automated reporting matures.
9. Support FHIR-based automated API usage metric reporting with transitional portal/form options.
10. Preserve standards version transition overlap and allow compatible Minor.Patch updates without new rulemaking.
11. Adopt FHIR under HIPAA only for prior-authorization-related referral/authorization and narrow eligibility checks, while preserving X12 for other eligibility transactions.
12. Require standardized conformance testing, leverage ONC Certification, and monitor production API availability and conformance.
13. Recognize vendors, PBMs, and delegated entities in compliance, reporting, and enforcement models.
14. Provide small-plan support through reference implementations, shared test tools, and low-cost compliance paths.
15. Align cybersecurity/resiliency expectations with HIPAA Security Rule and NIST.

## 7. CONCERNS & OBJECTIONS

- **Primary concerns:** Version drift from separately requiring base FHIR and IGs; immature FAST Security/CDex mandates; endpoint discovery friction; inconsistent payer API conformance; delegated-entity/PBM dependencies; small plan burden; overly broad replacement of X12 eligibility.
- **Potential negative impacts cited:** Broken production integrations, duplicated development, delayed patient/provider access, burden shifted to providers through portals, compliance exposure for plans that depend on unready vendors or PBMs, and fragile cybersecurity from bespoke point-to-point connections.
- **Implementation barriers mentioned:** Lack of scalable trust communities, limited production maturity for some IGs, manual endpoint reporting, inconsistent semantic mapping, PBM data dependencies, small-plan resource limits, and insufficient conformance testing.

## 9. IMPACT ASSESSMENT

- **Affected stakeholders:** Impacted payers, small health plans, MA organizations, Medicaid/CHIP programs, QHP issuers, PBMs, providers, EHR vendors, app developers, clearinghouses, technology vendors, patients, CMS, HHS, ONC, HL7, and NCPDP.
- **Economic implications:** Recommendations aim to reduce duplicative builds, redundant reporting, manual integration costs, and small-plan burden, while recognizing that conformance testing and standards support require investment.
- **Technical feasibility:** The core drug PA extensions are feasible if built on existing CMS-0057-F workflows; CDex, FAST Security, and broad FHIR HIPAA adoption require phasing and maturity checks.
- **Patient care impact:** Better endpoint discovery, prior authorization APIs, and conformance testing should reduce delays, improve access to drug PA information, and make APIs usable in practice.
