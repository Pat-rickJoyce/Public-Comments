**2. EXECUTIVE SUMMARY**
This comment addresses the critical gap between technical conformance to FHIR implementation guides and the practical usability of health data. While supporting CMS's advancement of interoperability through API requirements, the commenter identifies that fully conformant implementations can still transmit data that receiving payers cannot operationalize without manual review. The comment proposes five specific recommendations including semantic fidelity benchmarks, requirements for structured data transmission, round-trip scenario testing, public fidelity scoring, and clarification on segregated processing environments.

**3. REGULATORY CONTEXT**
- Specific sections/provisions addressed: Section III.C (Improving Implementation of Payer Application Programming Interface Technology); Section II.E (API endpoint registry); CMS-0057-F (2024 final rule); October 1, 2027 compliance date
- Regulatory citations mentioned: CMS-0062-P; CMS-0057-F; CMS-2026-1255-0001 (docket); Initial Regulatory Flexibility Analysis (Section V.F)
- Standards referenced: FHIR; HL7 FHIR Da Vinci Prior Authorization Support; Clinical Data Exchange (CDex); Payer Data Exchange (PDex); LOINC; RxNorm; RXCUI; NDC; DocumentReference resources; Observation resources; ONC Inferno reference implementation; HIPAA

**4. DETAILED POSITIONS**

**Topic: The Conformance Gap**
- Position: Concerned - Requires Additional Requirements
- Rationale: Conformance and usability are not the same property. Implementations can be fully conformant while emitting payloads that require substantial human review or manual re-keying. The rule does not require upstream payers to send data in a form that preserves operational meaning.
- Specific request: Address the gap between technical conformance and practical usability through additional requirements and testing.

**Topic: Unstructured Attachments Under CDex**
- Position: Oppose Current Permissiveness
- Rationale: CDex permits clinical attachments as unstructured DocumentReference resources (base64-encoded PDFs). Two payers can both pass conformance testing while one transmits structured LOINC-coded lab Observation resources and the other transmits scanned PDFs. Both are conformant, but only one is usable downstream without OCR and manual extraction.
- Specific request: Distinguish between structured and unstructured transmission in conformance requirements.

**Topic: Code System Fragmentation**
- Position: Concerned - Requires Standardization
- Rationale: Step therapy criteria, prior treatment failures, and contraindications are expressed in different code systems by different payers (RxNorm RXCUI, NDC, payer-internal identifiers, free text). Only standardized encodings enable automated processing; others require manual review.
- Specific request: Mandate encoding that preserves semantic specificity required for automated processing.

**Topic: Semantic Loss Across Payer-to-Payer Handoff**
- Position: Concerned - Requires Preservation Standards
- Rationale: PDex transfers are mapped multiple times (source system to FHIR to receiving system). No specification-level requirement exists to preserve or reconstruct structured decision logic. Members who cleared step therapy at one payer may be forced to repeat it at the next.
- Specific request: Require preservation of structured decision logic across payer transitions.

**Topic: Round-Trip Scenario Testing**
- Position: Support with New Testing Framework
- Rationale: Current testing tools (ONC Inferno) focus on endpoint conformance (API response, resource validation, bundle structure). No widely adopted test asks whether clinically meaningful scenarios can be transmitted and rendered into coverage decisions without semantic loss. Endpoint conformance tells nothing about whether system works for patients.
- Specific request: Develop and require round-trip scenario testing for high-stakes clinical scenarios.

**Topic: Patient Matching Quality**
- Position: Concerned - Requires Standards
- Rationale: Patient matching across payers is governed by internal algorithms. Conformant exchanges may transmit data for wrong patient or fail to resolve the same patient depending on demographic data quality and matching thresholds.
- Specific request: Set expectations for matching quality or transparency.

**Topic: Semantic Fidelity Benchmarks**
- Position: Strongly Support - Recommend Implementation
- Rationale: Benchmarks would measure percentage of data conveyed in structured, operationalizable formats versus unstructured formats. Publishing benchmarks creates market signal for quality even without being pass-fail gates.
- Specific request: CMS work with ONC, HL7, and Da Vinci Project to define measurable benchmarks for common clinical data categories (lab results with LOINC codes, medication histories with RxNorm RXCUIs, prior authorization decisions with structured rationale).

**Topic: Structured Data Transmission Requirements**
- Position: Strongly Support - Recommend Mandate
- Rationale: CDex permits but does not require structured attachments. When source data exists in structured form, payers should transmit it in structured form. PDF wrapping of natively structured data should be discouraged.
- Specific request: Establish that when source data exists in structured form within originating payer's systems, payer must transmit it in structured form across Provider Access, Payer-to-Payer, and Prior Authorization APIs.

**Topic: Reference Test Corpus for Round-Trip Scenarios**
- Position: Strongly Support - Recommend Development
- Rationale: Corpus would enable testing whether scenarios can be transmitted, received, and operationalized without semantic loss. Should cover high-volume and high-stakes patterns where fidelity loss falls most heavily on patients.
- Specific request: CMS, ONC, and Da Vinci Project publish reference set covering specialty drugs with prior step therapy, oncology with biomarker-based eligibility, transplant immunosuppressants, autoimmune biologics.

**Topic: Data Fidelity Score Publication**
- Position: Strongly Support - Recommend Implementation
- Rationale: Publishing fidelity indicators alongside API endpoint registry gives receiving payers, providers, and patients basis for understanding upstream quality. Creates market incentive for payers to invest in fidelity beyond conformance.
- Specific request: Include small set of fidelity indicators per impacted payer in API endpoint registry publication, derived from semantic fidelity benchmarks.

**Topic: Segregated Processing Environments**
- Position: Support - Recommend Clarification
- Rationale: Some payers may wish to operate dedicated, isolated environments for ingestion and normalization of clinical data for security and liability segregation. Consistent with HIPAA and minimum necessary access principles, but rule does not address.
- Specific request: Clarify that conformance and testing framework does not prohibit payers from staging, normalizing, or quality-checking ingested data in separate environment before promoting to operational systems.

**Topic: Implementation Timeline Considerations**
- Position: Concerned about Timing Tradeoffs
- Rationale: Adding fidelity benchmarks and reference test corpus on top of October 1, 2027 compliance date risks slowing implementation, particularly for state Medicaid Fee-for-Service and small Medicaid managed care plans with limited resources.
- Specific request: Consider phasing fidelity reporting separately from conformance, with fidelity benchmarks twelve to eighteen months after conformance compliance date.

**Topic: Risk of Premature Standardization**
- Position: Cautious
- Rationale: Tooling for semantic preservation across payer boundaries is still maturing. Locking in specific approaches before industry convergence could entrench suboptimal patterns.
- Specific request: Frame recommendations as benchmarks and test corpora rather than fixed technical mandates to allow approaches to evolve while creating accountability.

**Topic: Burden on Small Entities**
- Position: Concerned - Recommend Accommodation
- Rationale: Initial Regulatory Flexibility Analysis (Section V.F) identifies cost concerns for small payers. Fidelity testing adds incremental burden.
- Specific request: Consider whether fidelity benchmarks should initially apply only to larger payers, with smaller payers reporting on delayed timeline or under modified expectations.

**5. RECOMMENDATIONS**
1. Establish semantic fidelity benchmarks alongside conformance testing, working with ONC, HL7, and Da Vinci Project
2. Define measurable benchmarks for common clinical data categories: percentage of lab results as structured Observation resources with LOINC codes, percentage of medication histories with RxNorm RXCUIs, percentage of prior authorization decisions with structured rationale
3. Require structured representation when source representation is structured - establish that when source data exists in structured form, payer must transmit it in structured form
4. Discourage PDF wrapping of natively structured data through testing and certification framework
5. Develop reference test corpus for round-trip scenarios covering specialty drugs with prior step therapy, oncology with biomarker-based eligibility, transplant immunosuppressants, autoimmune biologics
6. Require payers to demonstrate scenarios can be transmitted, received, and operationalized without semantic loss
7. Publish data fidelity score alongside API endpoint registry, including fidelity indicators per impacted payer
8. Clarify compatibility of segregated processing environments for data ingestion, normalization, and quality-checking
9. Phase fidelity reporting separately from conformance, with fidelity benchmarks twelve to eighteen months after conformance compliance date
10. Frame recommendations as benchmarks and test corpora rather than fixed technical mandates
11. Consider applying fidelity benchmarks initially only to larger payers, with smaller payers on delayed timeline or modified expectations
12. Set expectations for patient matching quality or transparency across payers

Public Comment on CMS-0062-P
Docket: CMS-2026-1255-0001
RFI Addressed: III.C. Improving Implementation of Payer Application Programming Interface

Submitted by: Akken Yakupitiyage, Founder, Zkeleton
Introduction
I am writing as the founder of Zkeleton, a pre-seed company building clinical data normalization infrastructure for health plans. The recommendations below respond to Section III.C of the proposed rule, which requests comment on how CMS can strengthen testing, oversight, and certification of payer Application Programming Interface technology. Zkeleton is not a regulated entity under this rule, does not currently sell into any of the impacted payer categories, and has no direct commercial position in the outcome of this rulemaking. The perspective below reflects technical analysis informed by direct engagement with the standards documents, the relevant Da Vinci implementation guides, and conversations with leaders at Medicaid and Medicare Advantage organizations preparing for these requirements.
The proposed rule meaningfully advances interoperability by extending API requirements to drugs, expanding the scope of impacted payers, and establishing a centralized API endpoint registry. The recommendations below are intended to address what I believe is the most significant unaddressed risk in the proposed framework: the gap between technical conformance to FHIR implementation guides and the practical usability of the data those guides convey.
The Conformance Gap
CMS-0057-F and the proposed CMS-0062-P establish that data must move between patients, providers, and payers through specified API surfaces and implementation guides. The rules carefully specify the transport, the resource shapes, and the IG conformance requirements. They are largely silent on whether the data, once moved, retains the semantic specificity required for the receiving party to act on it.
This distinction matters because conformance and usability are not the same property...
